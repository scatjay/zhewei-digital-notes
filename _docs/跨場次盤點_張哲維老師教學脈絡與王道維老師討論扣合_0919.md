## 二、銜接關係

### 2.1 六步驟研究流程：只在第一場被明講一次，之後沒有再被點名，但實質上被拆解重組貫穿全程

第一場收尾處（`01:06:28–01:07:09`）明講的六步驟——①知識分類②快速記錄③思考凝結④數位分析（選）⑤書寫⑥知識共享——**在後面五場（含第六場）裡，張哲維老師沒有再用這六個詞的原文重新點名過一次**（跨場次逐字稿檢索「知識分類」「快速紀錄」「思考凝結」「數位分析」「知識共享」「六步驟」等關鍵詞，除第一場出處本身外全部零命中）。但這不代表這個框架被丟掉，而是被拆成好幾條線，分別在後面的場次裡重新出現：

1. **第一場自己的收尾動作，就是後面MCP要解決的問題**：第一場最後一步是把 Obsidian 筆記資料夾掛進 ChatGPT 專案，讓AI讀得到自己的筆記（`01:08:30`起）。第六場p16–17正式定義MCP（模型上下文協定）時舉的例子，本質上就是同一件事的通用化版本——「把AI工具跟外部資料庫／檔案系統串起來」。這條連結其實已經在第四場科普轉譯稿裡被指出過（該稿h2「昨天下午你已經做過一次MCP要解決的事」），本報告在此確認並沿用這個觀察。
2. **「流程化→系統化→自動化」是第一場自己埋的伏筆，AI Agent是那個「自動化」**：第一場講完六步驟後緊接著說「才有辦法把這個步驟進一步的流程化系統化甚至未來透過AI agent的方式進行自動化」（`01:07:09`附近）。第六場p13、p18正式定義AI Agent（「把LLM和工具整合起來變成能感知和改變外界環境的智能程序」）時，等於是把第一場這句預告技術落地。這條連結也已在第四場科普轉譯稿被點出（該稿h2「把研究流程六步驟交出去跑的，就是它」）。
3. **第六場p66–75的「五步驟」是六步驟前半段的技術深化，不是改名或替代**：這五步驟（①寫數位筆記②Markdown③JSON④CSV⑤TEI）講的是「同一份筆記在不同資料格式間怎麼轉換」，技術上對應的是六步驟框架裡①知識分類②快速記錄的具體實作方式，外加為④數位分析鋪路（JSON/CSV可以進向量資料庫、關聯式資料庫、圖資料庫，見p72）。**這裡要特別誠實澄清一點**：第六場科普轉譯稿的honest_notes已經明確提醒過，這組「五步驟」（投影片明確編號到「第五步」）跟第一場的「六步驟」是兩件不同的事，容易因為都是「N步驟」被誤認成同一套東西的兩種講法——本報告採用該提醒，在此把兩者的關係講清楚：五步驟是六步驟框架裡前段（知識分類/快速記錄/部分數位分析）的技術實作細節，不是六步驟的替代或簡化版。
4. **第六場p81–83的13步驟「學界共同資料庫工作流程圖」，是六步驟被AI Agent自動化之後最完整的落地版本**：研究想法→分析形成檢索指令→檢索→生成帶引註文章→反覆驗證→紀錄進資料庫→研究者人工反覆檢驗與修改→比對修改前後差異→最終確認文本，這13步驟粗略對應六步驟框架的全部六個階段（知識分類/記錄→思考凝結→數位分析→書寫→知識共享），且多了「AI自動生成」與「人工複核」交替的環節。**但這條連結是本報告自己讀完p80–83後歸納出來的觀察，張哲維老師本人在課堂上沒有講出「這就是回到第一場六步驟」這句話**——這點列入第五節的誠實侷限，不宜寫成他自己承認的銜接。

**小結**：六步驟框架沒有被後面場次「明講式呼應」過，但它的骨架（分類/記錄/凝結/分析/書寫/共享）確實在第六場被拆成好幾條技術線重新組裝了一次，且最終的13步驟工作流程圖幾乎是它的完整技術翻譯。這是五場合起來看才看得出來的模式，單場科普轉譯不會處理這種跨場次的結構對照。

### 2.2 第二場是承上啟下的「操作橋接場」，且留了一句明確的伏筆給第二天

第二場本身沒有在講新的理論框架，而是把第一場的筆記哲學（Obsidian、卡片盒精神）變成具體可重複的操作步驟（wikilink、標籤、Metadata、SQL、引註格式）。這場最值得注意的一句話出現在p144附近：老師示範AI輔助寫作時說「怎麼樣避免AI生成內容出現幻覺，我們明天會繼續講」——這是一句**明確的跨天伏筆**，第四場p4與第五場p4都確實接上了這個承諾（分別從「知識侷限性」與「上下文視窗侷限」兩個角度講幻覺成因）。這是整個五場材料裡少數幾處老師自己口頭承認的、有明確履行證據的跨場次銜接，值得特別標記出來作為「連貫性做得好」的正面例子。

### 2.3 技術深度曲線：第四場打地基、第五場練手感、第六場收攏理論，遞進合理但議程順序製造了誤導

如果只看議程標題（提示詞工程→AI史料對話機器人→優化研究工作流程），會覺得應該是「怎麼問問題」→「怎麼做一個史料機器人」→「怎麼優化流程」的線性順序。但實際講述的技術深度曲線是：

- **第四場**：只講最底層、跟AI Agent／MCP／Skill完全無關的東西——Token怎麼切、怎麼向量化、注意力機制怎麼算、上下文越長為什麼越貴越容易幻覺。這是純粹的機制層，全程沒有出現「提示詞工程」該有的內容。
- **第五場**：把第四場學到的「上下文有限」變成操作直覺（Context Window百分比監控、RAG如何精準檢索減少上下文負擔），同時第一次讓學員動手用Codex（沙盒核准機制），MCP與Agent Skill在這裡只以一兩句話「預告」，明確說「下午再帶大家實作」（p84）。
- **第六場**：把第五場預告的東西正式攤開講完整定義（Context/System Prompt/User Prompt/Function Calling/AI Agent/MCP/Agent Skill/Harness），並且明確回頭點名「我們早上也講過MCP這個工具」（p16）、「就跟前面用Codex一樣」（p14）——顯示老師自己心裡對這個順序是有數的，只是**官方議程的標題分配沒有反映這個順序**。

**判斷**：技術深度曲線本身合理遞進，沒有跳躍或無謂重複；問題出在議程標題把「第四、五場」跟它們實際要鋪墊的「第六場定義」錯位標記了，這才是「落差」的根源，而不是老師講課邏輯有問題。這點跟第三節的逐項比對結果一致。

## 三、技術工具教學一致性/進階性比對

這是本報告被楊老師特別交代的核心部分。以下逐項列出張哲維老師在不同場次教過的同一個或相關概念，附場次+頁碼出處，並明確判斷是「一致遞進」「新詞無鋪墊」還是「定義漂移」。

### 3.1 Context／Token／上下文工程 —— 機制→實務→形式定義，三場遞進良好，但有一處計量單位沒有明說換算

- **第四場p33–37**：機制層定義。Tokenizer（編碼）→Embedding（向量化）→模型運算→解碼，明確講「不見得一個字等於一個Token」。
- **第四場p110**：把「上下文越長，計算量呈指數型增長」跟「幻覺」直接掛鉤，並且明白預告「如何從提示詞變成上下文工程，就是我們下一節課要講的事情」——這是老師自己標記的、跨場次的正式伏筆。
- **第五場p4**：把「上下文視窗侷限」列為幻覺成因之一，是第四場機制解釋的直接應用，沒有重講機制本身。
- **第五場p62**：明確口頭承認「這都是上下文工程的一部分，我們下午才會講上下文工程的基本原理，現在先教大家怎麼操作」——跟第四場p110的伏筆前後呼應，形成完整的三場閉環（p110預告→p62再次預告並開始操作→第六場兌現）。
- **第五場p79**：Context Window用量監控的實務畫面，用的計量單位是「**字元**」（已用1%、剩餘79%、已用54K字元、還剩256K字元），並給出「50%以前安全、60–70%容易出錯」的經驗法則。
- **第六場p3–4**：正式定義「Context = LLM每次處理任務時所接受到的信息總和」，並列出各模型Context Window大小比較，用的計量單位是「**token**」（Gemini 3.1 Pro 105萬token、Claude 4.6系列100萬token）。
- **第六場p10**：正式命名「上下文工程」，呼應第四場p110、第五場p62的兩次預告。

**判斷**：機制（第四場）→實務監控（第五場）→形式化定義＋跨模型量化比較（第六場）三層遞進清楚，且有老師自己口頭標記的兩次明確伏筆與兌現，是整組比對裡連貫性做得最好的一條線。**唯一要指出的細節**：第五場p79用「字元」計量Context Window用量，第六場p4卻改用「token」計量模型的Context Window大小，兩個場次用了不同的計量單位描述同一類東西（AI能「記得住」多少內容），老師沒有在任何一場明講字元跟token之間大約的換算關係（一般中文語境經驗值約1.5–2字元/token，但這只是報告作者的常識性附註，材料本身沒有提供這個換算），對非工程背景的讀者而言，可能會誤以為「79%剩餘、256K字元」跟「105萬token」是完全不同量級的兩件事，實際上兩者衡量的是同一個維度，只是單位不同。

### 3.2 System Prompt／User Prompt —— 第五場已經在做，但沒有點名；第六場才正式命名並回頭定義

- **第五場p62**：實際操作已經在用「agents.md」檔案設定AI的「背景設定」（老師原話：「AI就是透過我們的agents.md這個檔案，知道你的背景設定，回過頭來告訴你答案」），這在概念上就是System Prompt在起作用，但**全場沒有出現「System Prompt」這四個字**。
- **第六場p6, p9**：正式定義「System Prompt=開發者在後台設定的規則和人格設定」「User Prompt=用戶直接說出的設定或命令」，並舉出具體例子（System Prompt：「我是一個蔣中正的歷史研究者，請不要直接給我答案，要一步一步、有邏輯地推理」；User Prompt：「蔣中正喜歡吃什麼？」）。

**判斷**：這是一個**「先操作、後命名」的落差**，跟MCP／Agent Skill的「先預告、後兌現」模式不同——第五場並沒有預告「這是System Prompt，我們下午再講定義」，而是直接用agents.md操作，卻沒有把這個操作跟後面第六場要教的正式術語做顯性連結。對現場學員而言，可能要到第六場聽完定義，才會回頭意識到「原來昨天上午操作的agents.md就是System Prompt」。這不是矛盾（兩場講的是同一件事，沒有衝突），但確實是五場材料裡少數幾處「操作在前、術語在後，且中間沒有顯性橋接」的例子，跟MCP/Agent Skill那種「明講式預告」比起來連貫性稍弱。

### 3.3 MCP —— 第五場簡短預告，第六場正式定義並明確回頭點名，遞進做得最清楚的一條線之一

## 四、扣合對準王道維老師的討論

### 4.1 第六場尾聲Q&A：史料結構化是否限制人文詮釋的辯論

**身分提醒（誠實標記）**：round2_final.json本身在qa-1、qa-3就把這位提問者標記為「自我介紹為清大物理系代表，即下一場報告人，研判即王道維老師，身分推測未確認」——這個推測有相當強的情境證據支持（自稱清大物理系、下一場報告人，第七場實際講者確實是清大物理系的王道維老師），但**材料本身沒有名牌式的百分之百確認**，本報告沿用這個「研判、非確認」的態度。

辯論內容（qa-1）：
- 王道維（研判）提出的質疑：「光是把資料結構化這件事情，好像就跟人文的研究有點矛盾。因為結構化意味著要有一個統一的方法……好的研究……往往正是作者本身對於這份資料的另一種獨特看法……如果真的把所有資料，用類似Markdown的形式結構化以後，它會不會反而限制了我們對這份資料的理解方式？」他進一步追問：「你一開始怎麼標註這些索引，就已經決定了你怎麼看待這些文字」——這是對「擁有寫入權限的人決定資料格式，等於排除了其他詮釋方式」的具體擔憂。
- 張哲維老師的回應分兩層：第一層說「結構化的目的其實是做索引，是讓研究者更快找得到東西……不是為了做量化分析」；被追問後，第二層回應是「我保留我本人原本的樣子，同時也進行一步的結構化，但同時也讓其他人……保留那種留下（原貌）的可能性」，並承認「這在技術上可能需要很多的討論」——也就是說，張老師自己也承認這個問題在第六場當下沒有被技術性地解決，只是提出了一個方向（結構化與保留原貌並存）。

### 4.2 第六場p26–32的「人文研究專用Harness」懸問，與第七場「讀伴」系統的直接技術回應

這是本報告認為**證據最紮實、最值得寫進去的一條跨場扣合**：

1. 第六場p27，張哲維老師在投影片上明確留下一句帶四個問號的懸問：「（人文研究專用的Harness？？？？）」；p32進一步定義他認為人文版Harness該重視的方向：使用者的個人特色、個人經驗、與他人的鏈結、共鳴，以及閱讀經驗、筆記文筆風格、工作流程、質量評估與資料驗證。
2. 第七場「讀伴」系統設計理念這一節（`651.9–1057.9`），王道維老師開場第一句話就是：「它的基本架構是這樣，就跟剛剛張老師提到的HARNET是同一件事」——**誠實標記**：round2_final.json的unresolved_notes明確記載「HARNET」這個詞兩輪校對都無法確認正確拼寫或所指，本報告依上下文脈絡（張老師剛講完Harness、時間點緊接在張老師發言之後、王道維老師自己說「是同一件事」）判斷這極可能就是指「Harness」，但這是推論，不是逐字稿本身給出的確定拼寫。
3. 王道維老師接著描述的「讀伴」系統架構——攔截學生與AI之間的原始對話、用system prompt做manipulate（不直接給答案）、用Hayden White meta-history四層架構隱藏分析文本、保留學生自己的表達與分支對話——**在功能上剛好回應了p32提出的兩個重點**：
   - 「保留原貌」對應qa-1裡王道維自己提出的「結構化會不會限制詮釋方式」的疑慮：讀伴系統的設計刻意讓「分析結果不會告訴學生，它是隱藏的」，且用四個學科（文學/史學/哲學/社會學）視角同時分析同一文本，避免單一結構化框架壓過其他詮釋角度。
   - 「個人特色、個人經驗」對應p32的重點：讀伴的摘要「摘要的是學生跟AI所講的話，和學生認為重要的東西，所以每個學生寫下來的都會是不一樣的東西」——這正是張老師期待的「人文版Harness要保留使用者個人特色」的具體實作。

這條線索意味著：第六場提出的開放問題，在緊接著的第七場裡，被另一位講者用完全不同的技術實作（不是MCP/Agent Skill那套，而是攔截式的system prompt manipulate＋隱藏式meta-history分析）給出了一個具體回應，即使兩人事前未必協調過（王道維在qa-1、qa-3的發言顯示他是第一次認真思考人文結構化的問題，不像是套好的），這個呼應仍然相當扎實。

### 4.3 「AI要不要對使用者透明」：兩人用不同方向處理同一類邊界問題

張哲維老師的Codex沙盒核准機制（第五場p62）把「AI能做什麼」的邊界控制權交給**使用者**：要求核准／代我核准／完整存取權，是使用者對AI行動範圍的把關。王道維老師的「讀伴」系統則反過來，把「AI原始輸出該不該讓學生看到」的邊界控制權放在**系統設計者（教師端）**手上：學生看到的不是AI原始回覆，而是經過system prompt manipulate與Hayden White架構篩選過的版本，且這個底層分析「不會告訴學生」。

兩人處理的都是「AI介入邊界」問題，但方向相反：張老師擔心的是「AI會不會做出使用者不想要的行動」（行動層透明），王老師擔心的是「AI會不會把答案直接餵給學生、抹殺學生自己思考的機會」（內容層透明，且是**刻意不透明**——對學生隱藏分析過程，是教學設計上的選擇，不是技術限制）。這是同一組「人文/教育工作者如何劃定AI介入邊界」大哉問下，兩條方向不同但都成立的具體技術路徑，值得寫入報告，但要誠實承認：**這個對照是本報告的歸納，兩人在現場都沒有把這兩件事直接放在一起比較過**，材料裡沒有王道維或張哲維任何一方明說「我們的邊界設計理念是相反/互補的」這樣的話。

### 4.4 誠實標記：沒有被過度延伸的部分

第七場其餘內容（小泰的三年成效數據、UPenn蘇格拉底式AI Tutor文獻佐證、讀伴的角色設計細節、教師端功能與推廣構想）跟張哲維老師的技術路線**沒有直接對話**，是王道維老師自己獨立的教育現場實踐與數據，材料裡也沒有任何一句話顯示這些內容是針對張老師的教學設計而講。qa-2、qa-4的提問者（分別關注感官/視覺資料的AI理解、世界史領域的多維度思維教學）跟王道維老師的技術路線更無關聯，是工作坊現場的一般性延伸討論，本報告不勉強把它們也扣進「王道維×張哲維」的敘事裡。
