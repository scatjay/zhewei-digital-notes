（現場廣播）各位與會嘉賓，活動即將開始，請盡速入座，謝謝。主持人：本次會議接下來進行的是第六場工作坊，有請張哲維老師，謝謝。張哲維老師：好，各位老師大家好。剛剛休息了一陣子，我們下午也是我個人的最後一場，好，努力把這場講完。那我想說在下午場開始之前，先把上午有一個小部分沒有結束的地方——也是我們這次活動最後操作的部分——把它帶完。那大家一樣，一步一步跟著操作，有任何問題都可以舉手發問，我們助理會協助。那就是我們最後 agent skill 的部分。

那剛剛這一系列的過程，就是這一年多、一年以來最流行、發展最快的，叫做 AI Agent。

我們要從生成式AI最新發展趨勢裡，來理解 AI Agent 的本質是什麼。如同前面所說的，這個本質基本上還是「上下文工程」的一部分。當我們問AI問題時，AI會把很多隱藏資料——包含過去的對話紀錄——全部壓縮起來，再發送給大型語言模型。比如說你只問「你好」這兩個字，表面上對我們來說只有兩個字，實際上電腦裡面已經把前面的對話紀錄、你過去使用過的內容，還有工具的內容，全部打包起來一起傳送給語言模型，佔了很多很多的文字量、很多的上下文，只是我們不知道而已。所以你會發現，問一個簡單的問題，其實會消耗大量的 token。語言模型實際上並不會記得前面的聊天紀錄，你每次問它，對它來講都是從零開始，那它為什麼看起來像是知道前情？就是因為有上下文在背後補足。使用者傳送問題時，系統就會把前面所有的東西一併加上去。上下文舉例來說，最典型的就是：對話紀錄、使用者的問題，還有工具列表。以前我們問它問題，它不會傳送工具列表；現在則是先把工具列表丟給語言模型，語言模型透過這個工具列表，就知道自己能夠呼叫哪些工具，並且在需要呼叫工具時，輸出符合這些工具所需引數與指令的格式，就有辦法去操作、控制這個工具。此外，上下文裡還會包括一些 System Prompt 或 User Prompt，還有一些臨時的記憶體內容，全部都會一併放進去。

那 Context Window 能有多大呢？其實 Context Window 是有侷限的，它通常大概以 Google 的 Gemini 3.1 Pro 來說，大概有105萬個 token，用量成長很快，但實際上用著用著就會發現都不夠用。這也是為什麼當我們的 token 越用越多時，它會變慢的主因；當 token 越來越多，它計算的結果反而會越來越有問題，出現越來越多的幻覺。

這張圖大概是我自己統合起來的，是2025年年底以來上下文工程領域發展的趨勢，這是一個很重要的東西，我會一個一個稍微講解。

我們以前 AI 剛出現的時候，講的就是「提示詞」。提示詞的意思是：我們要用怎樣的問法，AI才能給我們更符合需要的答案。所以有一陣子非常流行所謂的「提示詞工程」，就是研究要怎麼問，它才會告訴我們真正想要的東西。這就是提示詞，可是提示詞其實有兩種。

第一個是使用者的提示詞。使用者提示詞就是我們問它問題的時候，不管你問什麼，這就叫使用者提示詞。

另外一個叫系統提示詞。就像我們這幾天上課，不知道大家有沒有建立一個 MD 檔，叫做 agents.md，這就是系統提示詞。系統提示詞在以前 ChatGPT 的對話視窗裡，其實也可以自己設定：先跟它說你是一個怎麼樣的角色，比如說你是一個外科醫生，今天要幫某位老師動刀，該做什麼、做什麼。這樣它就會假設自己是一個骨科醫生，今天要動刀，一步一步該怎麼做——這就是系統提示詞，賦予它一個新的角色。

怎麼樣把提示詞寫好，這就是提示詞工程。之前有一陣子這非常流行——有時候不是AI不懂，而是因為我們寫得不夠精確，AI好像不知道你問題真正精確的意思是什麼，所以語言能力很重要，要能精確表達。舉個例子，System Prompt 可以這樣設定：『我是一個蔣中正的歷史研究者，請不要直接給我答案，要一步一步、有邏輯地推理，並且要以史料作為證據。』這就是 System Prompt。而 User Prompt 就是『蔣中正喜歡吃什麼？』這樣的問句，兩者合起來就是這樣一個過程。

接下來，後來逐漸發展出一個東西，叫做上下文工程。因為AI本身沒有記憶，所以它每次對話都是全新、空白的一次開始，那要如何把這個上下文工程做得更好，就變成一個非常關鍵的問題。而在上下文工程裡面，後來人們逐漸融入了一個工具。

接下來，人們逐漸把一個工具融入其中，叫做 Function Calling。Function Calling 的意思是，把AI裡面所有的工具——也就是電腦裡面所有的工具——都寫進去。這樣一來，這些大型AI廠商就能夠透過這樣的方式，去調控電腦裡許許多多的資源。舉個例子，假設我今天想要有一個查詢工具，我問電腦：『我今天想知道我的電腦裡有沒有關於某份資料的內容。』它就會呼叫電腦裡的一個資源，第一個就是索引——你的電腦一定有索引，索引會告訴使用者你有哪些資料。它搜尋之後，發現你曾經有一份資料提到那個關鍵字，就會呼叫它，知道要去哪裡把這個東西調出來，調出來就是讀取，讀給你看，知道這個東西是做什麼用的。而這整個過程其實都是用 JSON 格式去描述：我要怎麼呼叫、目錄在哪裡、要透過哪個程式去呼叫哪個工具，然後把它呼叫出來，再回傳給使用者。

有了 Function Calling 這個工具之後，我們慢慢發現AI能夠把很多工具整合在一起。舉個最簡單的例子，假設你要它去呼叫網頁資料，它就會呼叫 Google Chrome 這個應用程式；或者你想訂 Uber Eats，它可能就透過網路呼叫你的手機，把手機上的 Uber Eats 開啟，輸入你想吃什麼，然後幫你下單——這就是 Function Calling 一個很強的呼叫能力。後來隨著發展，它又做了一件事：我們以前寫程式的時候，GitHub 裡儲存了大量一種叫 diff 的檔案格式，這種格式基本上是記錄我每一次寫程式的過程中，哪些內容被刪掉、哪些是新增的，有一套編輯與歷程紀錄，概念上跟 Git 很像。大家只要想像一件事：我們有非常多這樣的紀錄，記錄著哪些程式出現什麼問題、又是如何修改的，這些大量大量的文字，被拿來作為訓練大型語言模型的基本資料。如此一來，AI就知道哪些程式碼是有問題的，哪些程式碼才算是正確的。

比如說我們早上用的那個工具，它為什麼知道工具的程式該怎麼寫？很簡單，因為它已經記錄了大量過去在GitHub裡寫這類程式的內容，當然知道要產生出怎麼樣的文字，才能變成一個可執行的程式，全部都能整合起來。所以像你的電腦、你的AI，都有辦法幫你寫程式，變得非常方便。我們把前面講的 Function Calling 跟 Vibe Coding，還有這些工具全部整合在一起，把整個系統化的過程統合起來，稱之為 AI Agent，也就是「AI代理人」。因為它看起來好像是一個人，能夠幫你做決策，可是它的底層其實還是圍繞在語言模型：你問它問題，它最後產生什麼答案，關鍵在於它如何透過前面所描述的這些機制，把工具呼叫出來。AI Agent 裡面通常會有預先寫好的一些程式，比如說 read 就是讀取，write 就是寫入，list 就是列出檔案目錄，同時還有很多 I/O 操作介面的函式。

這些整合起來之後，以後我們問它問題，就跟前面用 Codex 一樣：你剛問它問題，它就開始呼叫工具，你可以看到它一個一個列出來，說它呼叫了什麼工具，甚至呼叫失敗時，它也會告訴你『我失敗了』。當大型語言模型接收到Agent回報失敗的訊息時，就會做一件事——就像我們教學生一樣，如果一個學生作業寫失敗，你會叫他怎麼做？再寫一遍。所以一樣，Agent 就會告訴模型『再寫一遍』，如果還是失敗，就會提示『是不是少了什麼東西』，因為它知道通常寫失敗是因為缺了什麼，就會跟語言模型說該怎麼補上；語言模型重新判斷一遍，就知道可能少了什麼，再繼續呼叫。這樣一來一回，不用懷疑，這個過程是相當消耗 token 的。

每一次的傳送，我們問它一個問題，其實背後重複傳送了很多次上下文的指令，去讓語言模型運算，這個過程其實非常消耗 token。這樣一來，語言模型就有辦法控制電腦，幫你完成任何可以透過程式執行的工作。所以回到根本，語言模型本身還是一個機率生成的工具，只是它好像變得可以幫我們做某些部分的決策，或者幫我們省略掉許多我們不想知道、或知道也看不懂的東西，看起來好像什麼都能做，但它的本質其實沒有改變。這導致一個現象：程式設計好像變得零門檻。但這並不是真正的零門檻，而是說，對我們這些程式設計的門外漢來講，可以很快地生產出一個透過程式做出來的工具。有了這個工具之後，我們就可以進一步做很多事情。當然，對資工系的老師，或是專門開發程式的人來說，裡面還是有很多需要微調的問題，但這已經超出我們的範圍，本來就不是我們的工作。我們的工作是：讓程式設計變得容易——比如說我們今天要寫個網頁，早上不是說寫網頁變得很容易嗎？剛剛大家用的 skill 也是這樣做出來的。變得容易之後，我們就可以先做出一個雛形，再去跟資工系的老師或專家討論，如果要進一步做，會遇到什麼樣的內容與問題，才能夠進行更深入的討論。一樣，我們早上也講過 MCP 這個工具。

一樣我們早上也講過 MCP 這個工具，就是「模型上下文協定」，我們可以透過 MCP 去連接不同的資料庫。它的本質其實也是上下文模型，只是它輸出的內容裡，帶有能夠跟其他人或其他資料庫通訊的協議與設定。比如說你要查詢某個檔案館，你的帳號密碼可能已經先寫在 MCP 協議裡了，這樣兩邊連線之後，每次你問問題，它就會到那個檔案館，把帳號密碼輸入進去，取得許可權才能夠呼叫——就是這樣的過程。那就變成我們看到的……

這樣的代理人就出現了。剛剛提到，比如說我輸入『你好』的時候，真正傳給LLM的資料其實超過90K：User Prompt 就是『你好』兩個字，加上讀程式碼的注意事項——也就是用 Harness（這個概念等一下講）、如何管理記憶與上下文的說明、如何使用 Skill、當前的執行環境是什麼，還有各個子 Agent 的用途是什麼。比如說我今天給它一個指令，它會自行把任務拆解，把我給它的東西拆成不同的任務，分別丟給不同的語言模型或不同的 Agent 同時進行作業，再把結果匯回自己的 Agent 進行統合。它有時能自行拆解任務，也能把任務的先後順序自己排好，因為它透過前面所講的這些機制都能知道；此外還包含各個工具的詳細描述。大家也可以知道，光是輸入『你好』兩個字，背後就有90K的資料，這是一個很可怕的量。也就是說，這會消耗大量的 token，也會產生很多幻覺，這也是未來要解決的一個瓶頸所在。

我們來看一下 AI Agent 大概是這樣的架構，這是我自己畫出來的：使用者透過 Agent，Agent 讀取我們本地端電腦上的東西，再把這些東西丟給AI公司的聊天網站介面，這個介面透過網路通訊傳回去給該公司的大型語言模型，處理完之後再傳回來，透過介面顯示給你看。如果 Agent 判斷不需要再處理了，就把結果直接顯示給使用者；但往往即使是一個簡單的問題，這個過程也會反覆好幾輪才能得到結果。剛剛上課前，李老師也問我，未來會不會發展成：我們直接架設一個本地端伺服器，就不需要透過商業公司的語言模型，自己架一個語言模型？這是有可能的，只要有錢都做得到，有新臺幣就可以。所以如果你想要保護資訊安全，就必須把這些東西移到本地端——不只是使用者端，例如未來每個歷史系都有自己的一片 H200 晶片，就可以把運算搬進來，這樣就不會有資安疑慮。當然，這個過程需要大量資金，而且任何靠資本支撐出來的服務，一定都是最好最快的；如果我們自己架設，服務品質相信不會比現在用的 ChatGPT 更好，畢竟他們有最新的工程師、最好的技術，還有大量晶片在運算，當然比較強。

AI Agent 的基礎架構，我們前面講了這麼多，用意就在這裡：它有很多很多的工具，比如讀取日曆、計算機、程式碼直譯器，還有搜尋等等。它也可以把記憶分成長期記憶與短期記憶，進行記憶的壓縮——因為我們問問題時，有些內容是不需要的、可以被清除掉，盡量把 Context Window 壓縮、減少。它同樣有辦法透過「計畫」機制，做很多事，比如自我審查的反思機制、思維鏈的方式，以及子目標分解等。最後它有一個「行動」，因為工具可以被呼叫，進而執行行動。整個 Agent 就是靠這樣的基礎架構搭建起來的，而這一系列的過程，基本上都跟整個系統工程有很大的關係。說真的我們自己做不到這麼細的程度，但知道它有這樣一個過程就可以了。

舉個例子：假設女朋友說她肚子餓了。這時 Agent 收到這個問題，就會把它放進 User Prompt 裡，然後 Agent 透過 MCP 服務去檢查有什麼工具可用，發現有搜尋網頁的工具，於是生成一個 Function Calling 去呼叫網頁；呼叫完之後，發現 MCP 裡有 Uber Eats 的功能，就透過 Uber Eats 去搜尋『我想訂麥當勞』——因為根據過去的對話紀錄，知道女朋友喜歡吃麥當勞。Agent 收到後，就告訴 MCP：『請幫我在 Uber Eats 上訂這個麥當勞。』訂完之後，系統回覆說要付款，於是信用卡的 MCP 又出現了，透過信用卡 MCP 呼叫資料完成付款，自動付款完成後，廠商收到款項，就準備好餐點，讓外送員送到你家門口，你下樓拿就可以了。你會發現，這整個過程只做了一件事：女朋友說她肚子餓了，最後麥當勞就送到家門口。這裡面很關鍵的一點是：為什麼一定是麥當勞？或者說，為什麼一定是某一種食物？對 Google 這類商業公司來說，這裡面有非常強的商業可能性——因為你要吃什麼東西，看起來是隨機生成的，但只要看起來隨機，就有可能是廠商置入。比如說，假設我家門口旁邊賣米粉湯，我就去跟 Google 買廣告，說當方圓幾公里內的人說『肚子餓了』的時候，請優先推薦這鍋米粉湯，放在第一個位置——這跟過去關鍵字搜尋的邏輯是一樣的。而且問題是，人本來就是懶惰的，反正它推薦什麼，我就吃什麼，米粉就自動送到你面前，你根本連選擇的機會都沒有。這也是有可能的——就像我們前面講的「沙盒」，全部交給AI決策，99%的人都會選擇交給它決策，因為我們都很懶惰，懶惰是人的本性，最後米粉湯就這樣大賣了。這就是一個過程。

Skill 的概念也是一樣：Skill 就是透過一個 .md 檔案的資料夾——skill.md 檔案——把剛剛那一系列拆解的過程先寫下來。然後每次電腦在執行、Codex 在執行的時候，就會先去看每個步驟是否都設定好了，告訴它東西放在哪裡：第一步是要把什麼檔案分類好，第二步是要做 OCR，第三步是把 OCR 結果拿去翻譯。這整個過程都事先寫在 Skill 裡，它每進行一步、要進行下一步時，就會回去讀一次 Skill，知道下一步該做什麼，再繼續做，就這樣反覆、反覆、反覆，最後就變成我們剛剛帶大家實作的那個樣子。你就會知道，這個過程看起來好像很厲害，其實說穿了也沒有多強，就是這樣子而已。

然後 Harness 的意思其實也很簡單。前一陣子AI圈子裡吵得很多，我每天早上都會聽到大家在講這個 Harness 發展得多厲害，其實關鍵很簡單：就是把 AI Agent 這樣的流程系統化，進而控制語言模型，讓它更符合規範——比如說資安規範，或更符合人的需求，並且創造出一個以大型語言模型為核心、穩定運作的工作系統，讓語言模型替人們做出一些決策與判斷。人只需要去思考自己想要什麼，以及做最後的判斷跟檢查而已。

也就是說，透過一些工程技術，把前面那些看起來很分散的 AI Agent 元件，進行系統化的整理，僅此而已。那我們真正該問的是：剛剛講的這些東西都是誰做的？都是商業公司，或者是某些工程師，思考的是符合他們自己需求的 Harness 設計。那問題來了：我們人文研究有沒有辦法，設計出屬於自己人文研究的 Harness？或者說，我們的研究到底有什麼樣特定的流程？這是我們未來可以去思考的問題。

簡單來說，回歸到根本，不管是 AI Agent 或是大型語言模型，關鍵都在於使用者需求到底是什麼。所以某種程度上，人們似乎變得不用親自執行，但物理上的執行任務並沒有消失，只是變成了不同的形態。人的核心職責已經開始改變，變成要如何建立一個穩定可靠的系統架構，來支撐這個框架，進而提高工作效率。從人文學界來講，我們就要去思考：AI Agent 確實有可能重塑人文學界的工作流程，甚至重塑整個學界未來的運作機制，這是很有可能的。關鍵可能就在於，我們到底要的是什麼。

所以我們可以看到，AI Agent 從2025年年底到現在，一系列演變的過程可以歸納為：提示詞工程告訴我們怎麼「問」，上下文工程告訴我們怎麼「記」，而 Harness 工程告訴我們怎麼「管」——這是一系列發展的歷程。

那其實關鍵在於：我們該如何設計一個符合歷史學研究、人文研究，或者寫作創作流程的 AI Agent？這一點，我想等一下下一堂課，可能會有老師稍微再講一下。

回過頭來說，人文研究的 Harness 工程有什麼不同的地方，或者說有什麼特點、我們應該重視什麼？就跟我昨天講的一樣，其實我們要強調的是使用者的個人特色、個人經驗，以及與他人的連結或共鳴，還有我們的閱讀經驗，以及我們筆記裡的文筆風格——這些東西都可能是我們必須重視的。同樣地，人文研究的工作流程、質量的判斷，還有資料的檢證，也都非常重要，如何把這些統合在一起。

那我稍微介紹一下：前一陣子這位先生做了一件非常重要的事，他還比我小一歲，他就是我們最近很有名的 OpenClaw——也就是我們戲稱的「龍蝦」——的設計者。

龍蝦背後其實有點複雜，我們基本上用這張圖來說明就好。其實「龍蝦」這個玩笑話一度很流行，前陣子大家都在「養龍蝦」，因為連中國大陸那邊也在討論，但過了一陣子之後，這股風潮好像就過去了。其實它的原理很簡單，就跟剛剛講的架構一樣，只是它把「網路通訊」也包含進了整個框架裡：透過網路雲端服務、網路通訊協定，把這些能力包在 Agent 裡面。這樣一來，人們只要透過手機，就能夠遠端控制自己遠端的電腦，甚至可以同時操作很多台電腦，每台電腦裡都有屬於自己的 Agent，你就可以控制裡面所有的東西。在這種情況下，使用者可以透過問一個問題，把任務拆解，分派給各台雲端電腦，處理完之後統合起來，再回傳到你的手機。我自己的手機前陣子就請工讀生幫我安裝了 OpenClaw。比如說我走到戶外，看到台灣的寺廟有很多匾額，就把它拍下來，說『請幫我記錄』，它就會幫我把內容記錄到電腦裡；或者匾額上有些文字，請它幫我分析，它分析好之後，也能直接存到我的電腦裡。所以我透過手機，就能夠遠端控制我許多台電腦。簡單來說，它就是把網路通訊也包含進整個 Agent 設計的範圍裡而已，簡單來講就是這樣。

當然這裡面其實有很多很多的設計細節，比如說路由器要怎麼分配、任務要怎麼排隊之類的東西——這些我們就沒有時間，直接跳過、跳過、跳過。

也就是說，其實你會發現，不管怎麼樣的變化，關鍵始終在於：我們到底需要什麼。我再講一個例子，對我們來講可能更貼近現實：假設今天教授晚上十點寄email催你交期末報告，跟你說明天一定要交。OpenClaw 收到信之後，發現是教授寫的信，判斷非常緊急，就讀取裡面的內容，並根據內容與你過去的email紀錄，知道你修的是哪一門課、明天一定要交報告。於是它馬上自動到網路上搜尋可能的摘要——這整個過程都是自動的——然後呼叫通訊軟體，把這個緊急訊息告訴你。你知道這件事之後，就告訴 OpenClaw：『請幫我生成期末報告，題目是某某某。』OpenClaw 收到之後，第一件事是蒐集教授的資訊、理解教授的偏好——比如說知道這位老師研究的是中德關係史，就會去找中國經濟史跟德國相關的網路資料，整合起來；接著檢視你過去的信箱內容，理解你過去期末報告的要求與方向。基於這些資料，它再呼叫資料庫——假設資料庫是開放的——下載裡面相關的史料，自動完成 OCR，儲存成 Markdown 筆記，再根據這份筆記與網站內容，檢視相關著作，了解當前的研究趨勢。最後，OpenClaw 根據教授的偏好、史料，以及當前研究趨勢，生成一篇文章，並根據 Markdown 筆記加上可供查證的註解。生成報告之後，由於截止時間快到了、明天就要繳交，它還會生成一封文情並茂的道歉信，說明報告仍有不完美之處，請教授多多指教。最後，OpenClaw 呼叫你的email權限，把報告和道歉信一併附上，在期限前寄出。這整段期間，你其實都在睡覺，什麼都沒有讀過。教授收到信時，可能會誤以為你是熬夜完成的，非常感動——內容有史料、有文獻回顧、有對當前研究的關懷、又有註解、又有道歉信，感動加分。這在未來是非常有可能發生的。我不是要嚇大家，但這一系列的過程其實正慢慢地被串連起來，是很有可能發生的——你其實根本都在睡覺，連看都沒看過，對不對？

那期末報告到底該怎麼辦呢？也許真的要改成手寫的方式，或者說完全讓學生現場手寫；它甚至有辦法模仿手寫，因為它讀過大量手寫稿件，學過手寫的風格，也有辦法應付現場考試。這很有可能是這一兩年內我們教學現場會遇到的狀況。其實重點已經不在於報告內容有多好，而在於它可以在不需要休息、人無法工作的時間裡自動完成這些工作。當然這個過程中也有很多安全性、個資保護，以及其他大大小小的問題，就跟前面劉老師說的一樣，AI根本的問題還是在於倫理，這是一個很大的關鍵，也值得我們之後好好思考。

這時候你會想一個問題——我接著要講的是：為什麼是 Peter Steinberger 這個人，他應該是奧地利人吧，能夠打下基礎、做出 OpenClaw？第一個原因，是他具有專業的通訊基礎知識，比如網路、系統工程與環境配置；第二，他非常了解自己實際工作時的工作流程；第三，他知道自己的目標與需求；第四，這個需求是大多數人都需要的，而且具有可延展性；第五點很重要，就是他嘗試新事物的好奇心；第六，他在這個專業領域能夠不斷自我學習；第七，他不怕失敗，有承受失敗的底氣。

其實說真的，我要講這個的用意是什麼呢？這不也正是我們未來面對AI時，都應該具備的態度嗎？第一，我們必須要有自己的專業——歷史學的知識；第二，我們必須知道自己在操作歷史學研究過程中的工作流程是什麼；第三，我們要知道自己的目標與需求是什麼；同樣第四，我們的目標與工作需求，未來設計出來的東西，可能大多數同行——比如人文學界或歷史學界——都能夠使用；當然第五、六、七點，也都是我們學習新東西應該具備的基本態度。有了這樣的眼光跟想法，才能夠做出未來真正符合我們自己需求，或這個學界所需要的新工具。所以這就是我們應該要問自己的一個問題。

所以這就是我們應該要問的一個問題。當然我還想了很多很多，我們最後來講一下未來展望的部分，也算是最後的結論。看看還有三十分鐘的時間，對吧？好，我講得算快的，這兩天下來，我大概講了五節課了吧，好。

我一直認為，AI基本上是一場不可逆的典範轉移。而這樣的轉移，不只是理論上研究視野的轉向，而是更大、更全面、影響更深遠的變化，甚至對整個歷史學以及人文學界之所以稱為科學，從研究方法上重新定義，乃至於在人類整體知識中意義的重塑。當然，它既是危機，也是一個轉機。

我一直認為，AI時代下的數位人文工作，應該以人文研究為基礎作為主要的工作方向，這樣的建設基本上應該從五個點來思考：第一，我們如何強化史料或研究資料的可驗證性、可追溯性，以及可糾錯性；第二，我們應該建立一個統一的資料結構儲存，甚至是一個算力中心，當然這些都需要大量的經費；第三，我們要從使用者或研究者的視角出發，強化所謂的UI介面設計，這非常重要，因為任何好的工具，都應該建立在即便你不懂它的原理、或習慣過去的方法，也都有辦法快速學習的前提上，而不是把東西做得很難用；我覺得第四點更重要，就是如何建立一個共同培育的平台，讓這些AI相關的知識能夠更快融入教學過程，讓教學變得更容易；當然第五點也很重要，就是如何強化我們研究成果的推廣。為什麼要特別講第五點？很簡單，前面這四點每一項都需要錢，可是當我們沒有辦法跟社會大眾說歷史研究很重要的時候，社會在分配資源、想像資源分配方式的時候，當然不會把歷史學考量進去。有錢能使鬼推磨，那是真的，對，那是真的——我這樣講有點失禮，不好意思。那這是我的一些想法。

至於AI的本質是什麼，我相信今天跟昨天已經講得很清楚了。它是一個擅長分析、分類的深度學習系統，但它沒有情感，也沒有歷史經驗，更沒有道德感，這是一個很重要的問題。

它就是以一顆石頭為核心創造出來的東西，用來記憶人類、記憶個體資訊——一種人類本身無法比擬的訊息量。所以我們其實不能夠直接把基於統計、大數據運算，以及自然語言分析為核心的電腦系統，直接套用到人文研究的教學上面，否則我們很容易失去方向，甚至失去人文的溫度跟深度。

那我覺得為了要保有人文學科的特性，我們必須將AI視為一種輔助的工具，而不是一種全知全能的上帝。我們有時候對它產生的幻覺，或對它產生的錯誤理解，其實是源自於我們一直以來，好像都想要依靠一個全知全能的上帝，或是把所有東西都丟給工具，但其實這個想法是不對的。我們要思考的是：哪些步驟可以利用AI，讓它變得更有效率，甚至能夠集體合作，讓這個學界的未來能夠變得更好。所以我認為，當前人文面對AI這個深刻變革的關鍵節點上，不僅僅是攸關文化主體性、或知識自主性的任務，某種程度上，它更是守護人文價值、延續歷史記憶，甚至支撐民主社會的堅實基礎。為了達到這個目標，我覺得我們不能只是被動，而是應該更主動地出擊，重新去思考人文的定位跟角色到底是什麼。

當然大家昨天也講到主權AI，其實我很早就把這個寫進去了。首先我覺得，人文領域當前最大的任務，是深刻認識到自己在建構主權AI這件事情上肩負的使命。我覺得唯有如此，才能夠進一步鞏固從我們、從台灣為核心立場出發的歷史話語權。我們可以設想一個現象：如果未來中國大陸擁有這麼強大的大型語言模型、這麼龐大的資料，久而久之，最後能夠留下來的，可能只剩中國大陸的AI系統。到那個時候，未來也許就不會再有「台灣」這兩個字，或者說「台灣」這兩個字，會被他們產生非常非常大的誤解。

所以其實我覺得，我們應該以「智慧人文」——我自己這樣稱呼——的理念，來回應AI時代的變革。這個理念的核心其實很簡單，就是回歸使用者的主體性，而不是讓人文變成被動、遷就既有現成工具的樣子，而是從人文科學本身的研究邏輯，以及實務的研究流程出發，再應用上AI技術。

透過這樣的路徑，我覺得才能夠強化我們人文研究一直強調的可驗證性、可追溯性，跟可糾錯性。透過這樣的理念，用AI技術來強化人文研究的正確性，我覺得才能夠讓我們的歷史研究在未來的AI時代下，更具有說服力以及主體性。如此一來，才能夠避免、甚至防止歷史被扭曲，或文化被滲透的可能性，進而有力地去抵禦錯誤訊息對主權意志跟集體記憶的侵蝕。我覺得唯有如此，我們才能夠提出更加令人信服的歷史觀念，因為我們的歷史觀念都能夠回歸到史料本身，才能夠進而鞏固我們對歷史話語權的重要武器。這對台灣來講，未來是一件非常重要的當務之急。

與此同時，我覺得智慧人文不只是理念，而是要有具體的行動來推動它。例如我覺得專題式的教學就很重要，因為透過專題式的教學，才能夠驅動學生更有主動積極的學習動力。其實在AI的發展下，你會發現一個現象：老師學習的速度一定比不上年輕學生，但我們不見得要什麼都會才能教學生，我們很重要的角色是「引導」。我印象深刻的是，我姊姊的英文能力很差，但她教出來的小孩英文卻很強，她的能力其實比小孩還弱，她唯一做的事情就是盯著孩子、告訴他該怎麼做、每天要做什麼——這種「引導者」的角色是很重要的。同樣地，透過這樣的方式，也可以讓人文的學生透過AI技術，也讓理工背景的學生了解什麼叫做人文關懷的價值。在這種跨領域的對話之中，讓學生結合AI與人文的專業，創造出跨領域合作的可能性，共同思考如何把技術應用在學習、文化策展、館藏查詢、資料整理與整合等不同領域。透過這樣的實踐，我覺得能讓人文知識走出象牙塔，進而變成具體的、有潛力與社會價值對話的應用可能性，並且連結到產業應用，這很重要——讓社會了解人文的價值，也讓產業重新連結人文的深度。

那未來技術的突破會在哪裡？不是算力，也不是演算法——算力是台積電的事情，演算法是數學家跟資工系的事情——我們唯一的工作，就是要理解人到底需要的是什麼。那我的想法其實也很簡單：我們應該要正視人的侷限跟軟弱，讓我們創造的工具來彌補我們的不足。

同時也要能夠認知到AI工具本身的侷限性——它不能夠取代我們思考、情感、道德，以及個人的獨特性，更不能替我們做出決定。也就是說，AI其實不可能代替我們活著，只有我們親自去體驗這個社會、體驗這個當下，這才是人的價值之所在，這也是我認為人文最重要的地方。

那具體該怎麼做呢？我有一些建議。

首先，AI本質上就是建立在大數據的基礎上。我們不同於理工科系，他們早就有一套研究資料的共同架構；可是歷史學界在沒有資料基礎的情況下，很難進行具體的AI運算。所以我覺得面對AI的第一步，其實不是匯入任何工具——工具其實學得很快，這一兩天下來，大部分的人都已經有辦法上手，回去再多接觸幾次就可以了——更重要的第一步，是要有數位思維以及資料的概念。這件事我們長期以來都在培養，但未來透過AI的教學，這個培養的腳步應該要更加加速，這很重要。

第二點——我又會講到跟前面重複的東西，沒關係——就是在教學現場，我們其實很害怕用生成式AI，因為學生只用AI生成內容給我們，使我們難以驗證；我們在做研究時，也害怕產生許多錯誤或幻覺，讓我們在審查時常常出問題，進而動搖歷史學作為一門科學的根本。但事實上，AI並不是造成問題的本身，它只是反映並加速了我們長期以來沒有善用新技術，來強化自身科學性的問題，日積月累，才導致人文學科作為科學性的危機。

可是我們其實一直很清楚地知道，任何科學——除了數學跟哲學以外——它的科學性，都來自於某種假設前提之下的邏輯推演，以及合理性的推斷。歷史學的假設前提，就跟我們前面講的一樣，是傅斯年所說的史料；他沒有明講的是，我們經常做的一件事叫做「引用」。引用的意義在於：我們認為史料應該具備某幾種特性，來強化這種科學性。可是過去我們的文章，基本上都是信任作者的引用，甚至是無條件的信任——這是一種基於善意推定之下的信任。所以我們才沒有利用資訊技術，來強化這些特性。如果我們沒有建立一個共同的歷史資料中心，讓文章的引用或史料能夠被快速找到，更沒有要求作者提供這些原始資料，那我們又如何能把這些龐大的資料統合在一起？沒辦法統合，我們就會越來越難以驗證。所以我們以後一定會不斷遇到學生生產假資料的狀況；而如果他生產假資料，我要求它必須能夠被我們驗證，這就變成一個非常重要的關鍵。那回歸到底層，這些資料的結構，不是 Markdown，就是 Python，要不然就是資料庫，其實底層的東西很簡單。就像我這兩天講的關鍵，第一步都還是要先寫數位筆記。

比如說像 GIS 地理資訊系統、社會網絡分析，或者是 Text Mining 文本探勘，這些東西我們都要進一步思考，如何透過 AI、透過 Vibe Coding 的方式，把這些工具全部做出來。還有比如說經緯度查詢工具，這也很重要——我上次聽李宗慶老師演講時，他提到自己曾經想查自己家的地址，我心想，這種功能應該也可以整合進來。

那 RAG 能夠強化我們資料的可驗證性，而 AI Agent，我覺得未來真的是一個非常重要的關鍵。

AI Agent 能夠整合前面講的所有功能，甚至能把研究流程加以自動化、流程化跟系統化。我認為，我們在大型語言模型的開發上，比如說像台灣，絕對不可能超越中國大陸，或者說根本沒有機會，因為成本問題，我們不可能贏過中國大陸。但是，這幾年的發展也讓我們發現一件事：大型語言模型的開發，在資料量無限增長的情況下，必然會出現邊際效益遞減的情況，也就是說，大型語言模型未來一定會遇到一道牆——不管再怎麼訓練，最後都會趨近於這條線，無法再突破。原因有兩個：第一，資料已經蒐集到蒐集不到更多了；第二，算力再怎麼算，演算法的概念，就是在既有的架構裡面去運算，算久了一定會產生邊際效益遞減，逐漸趨於「熟練」的結果。所以大型語言模型未來一定會出現：投入很多很多資源，最後只能進步百分之一、百分之二的現象。這種現象現在已經出現了——確實，GPT剛出來的時候，進步幅度可能從百分之一躍升到百分之八十，但從那之後，變化的幅度就越來越小。而且相較之下，大型語言模型的開發需要非常非常多的錢，我們不可能去做這些事。但是 AI Agent 的開發雖然也需要成本，相較於大型語言模型會低很多。所以我認為，AI Agent 是可以讓我們未來從自己的需求出發，去架構、強化歷史學根本核心精神的一個非常重要的可能性；而且正因為 AI Agent 開發不需要那麼大的成本，我相信身處在自由國度台灣、一個真正具有歷史學術自由的地方，才真的有可能做得到——開發出符合歷史學研究需求的 AI Agent。

其實從大概七八月開始，我就一直帶著學生在思考——就是剛剛大家看到、還在外面休息的那幾位學生，當然不只他們，大概有七八位學生，一直在思考我們如何能在有限的資源之下進行開發。當然我畢竟是歷史學家出身，前面講的這些東西，剛剛曾老師也說我講得好像資工系的老師一樣，但其實我的了解真的有限，跟真正製作這些系統的專業人員還是有很大的不同，這些技術能力，其實都必須靠學生來幫忙才做得到。但我覺得，正因為資源有限，才更應該借助資工領域專家的協助，比如說我們跟成大的敏求智慧運算學院，或是下一場的講者王道維老師，其實都可以共同合作。而這整件事情最難的，其實不是硬體裝置，也不是技術問題，最難的其實是人才培育，還有歷史學界如何清晰地表達出自己的需求。我們下一堂課，可能可以跟王老師們一起討論這個問題。那另外一個問題，當然就是資料安全的問題——也許能夠透過區塊鏈，來解決這個資料安全的問題，這也是要進一步跟專家們合作的地方。

如此一來，假設我們收集了大量資料，就可以建立人文學界的標準測試，也就是 Benchmark，進一步把語言模型最佳化，讓它更符合歷史學家所需要的語言模型——但這個前提是要先有資料。

同樣地，人文的資料，不能只有閱讀，更重要的是——不能只有資料本身，而是要記錄人們閱讀之後，能夠激盪出怎麼樣的想法。如果我們能把這樣的資料全部記錄下來……

……那未來這件事，可能就是突破AI現有瓶頸的關鍵所在：人如何產生創意？如何產生靈感？如何產生想法？這可能是未來最重要的一個關鍵。

那如果我有這些資料——我自己想過這件事——如果我有這些資料，我以後就可以賣給 Google，賣給他們換取一大筆錢，然後我們就可以把自己的系統做得更好。這正是他們想要的東西：有了這些資料，他們才有辦法突破現有AI的瓶頸，對吧？而這些資料，不外乎就是我們歷史學者在閱讀、在日常生活中所產生的思考過程。我們只需要做到：閱讀的時候把筆記記錄下來，大家再把它整合在一起，就能夠為這個學界創造更多的可能性。利用收集起來的這些資料，就可以知道人是如何產生靈感，甚至能夠探究語言中最難的地方——言外之意。這個東西，AI也很難做到，但這個言外之意，往往才是我們研究突破的關鍵。我看過很多材料之後發現，表面的描述其實都沒什麼，AI只能讀懂表面的描述，但我們要如何理解語言之外、它真正想訴說的故事跟內涵？這不正是我們歷史學家真正想要探究的東西嗎？這是非常困難的地方，但這個地方需要研究者有很長的研究經驗、很深的歷史見識，以及很多的累積，才有辦法做到，而這是AI做不到的。

那我其實想做這個開發，原因很簡單。我最終的目標是希望，歷史學家未來只要讀書跟思考、挖掘史料跟解讀史料、還有教學推廣跟社會對話，就可以了——這就是我的目標。

其實這個目標說穿了就是懶惰——我想開發一個很厲害的工具，讓大家未來只要做這幾件事，就能夠應付AI。但我也知道這很難，這個過程要花多久，還有很多很多的工作要做。不過正因為AI讓這類技術變得更容易學習，這三件事——理解人的需求、由人產生的資料、基於人自身經驗產生共鳴才有意義——永遠不會被取代，所以大家也不用太擔心。

最後最後最後，我想留一點時間讓大家討論。我一直覺得，人文才是人類知識的目的。數學、物理、化學、生物、語言，甚至是人工智慧，都只是人類創造的一種工具。工具真正的目的，其實是輔助人們留下能與他人產生共鳴的事物。比如說，我們今天所擁有的「唐詩三百首」這些文學作品，正是因為能夠讓人產生共鳴，才有辦法永恆流傳——這才是人文的目的。而前面提到的這一系列不同學科，其實都只是我們的工具。所以我一直認為，人文才是知識本身的目的。

可是現在這個順序好像有點本末倒置，我一直覺得很奇怪。但是，我們學生物幹嘛？學醫學幹嘛？無非是要讓我們生活得更好，能夠創造出更好的文學作品，或成就更好的歷史作品，讓人產生共鳴。所以歷史、人物、文學、藝術，才是人的核心價值；醫學只是讓我們生活得更好，物理化學也一樣，是讓我們的工作與生活變得更好——我們能吹冷氣，這些都只是過程、只是工具。但我真心覺得，人文才是核心目標。所以雖然魯正恆老師今天沒有來，但我跟他討論了三次，我真心地跟他說：我覺得二十年後，歷史學才會變成聯考榜首第一名所填的科系，而不是其他學科。我跟大家講了林林總總的一堆內容，希望大家能在這五堂課的過程中學到一些東西，當然我也省略跟減少了很多內容，大家回去可以透過楊志傑老師開發的那個工具，很快地複習、再看看我到底講了什麼，在操作的過程中再學習一次，可能會理解得更多。因為我們大概還有三十分鐘的時間，想開放給各位進行討論。謝謝各位，謝謝。

提問老師（自我介紹為清大物理系，即下一場報告人，研判即王道維老師，身分推測未確認）：不好意思，我是清大那個物理系的代表，就是下一場要報告的人。不過謝謝剛剛你們的分享，我想請問的是——我也曾在別的不同場合，跟一些人文領域的學者討論過這件事情，但我感覺到一個問題，我也認為是真實存在的問題。他們好像——對不起，我說『他們』，也許是在座各位，讓我稍微這樣講——會覺得，光是把資料結構化這件事情，好像就跟人文的研究有點矛盾。因為結構化意味著要有一個統一的方法，來定義資料的重要性或它的性質；但也許好的研究，不一定是歷史研究或文學研究，往往正是作者本身對於這份資料的另一種獨特看法，和別人有所不同，以至於能夠跳脫傳統的框架，對不對？那如果真的把所有資料，用類似Markdown的形式結構化以後，它會不會反而限制了我們對這份資料的理解方式，反而讓人文研究一直失去那個特色，變成只是一種資料整理而已？我覺得這的確是我沒辦法完全回答的問題，但我也覺得這可能是很重要的問題，不知道您作為一位人文學者怎麼看這件事情？

張哲維老師：我的看法完全相反。我認為，所有資料的結構化，它的目的其實是做索引，是讓研究者更快找得到東西。之所以很多人會誤解，把結構化跟拆解畫上等號，是因為他們把結構化的metadata拿去做統計性的、量化式的分析；但其實結構化就跟做數位索引一樣，它一開始的目的並不是為了做量化分析，而是讓研究者更容易找到資料。所以對我來說，這可能不會是太大的問題——透過這個過程，我把資料結構化，但我仍然可以很容易地找到它；無論如何，我們終究還是要回歸到文字本身，還是要自己去閱讀跟理解。

提問老師：不，不好意思，其實有件事情——你講的結構化是文字的內容，這部分結構化當然可以容易找到；可是很多時候，這是關於我們對這些資料的理解，那個部分，可能每個人的看法、整理的方法都不一樣。同樣一篇文章，每個人看、整理出來的結果都不一樣。那如果你要把它放進一個統一的資料庫裡，它必定會有一個standardize（標準化）的方式，這樣一來，就會是那個擁有寫入權限的人，他就有權利去決定：這些資料該用什麼方法、這些文字該用什麼樣的資料格式來寫入——這樣一來，它可能就排除了另外一種對這些文字的詮釋方式。所以這個問題，不只是索引的問題，你一開始怎麼標註這些索引，就已經決定了你怎麼看待這些文字。

張哲維老師：所以我的解決方式是：我保留我本人原本的樣子，同時也進行一步的結構化，但同時也讓其他人在進行結構化的過程中，或是自己結構化的過程中，保留那種留下（原貌）的可能性。但我知道，這在技術上可能需要很多的討論，跟很多的思考，怎麼能夠做到——你同時也能夠保留原本我本人的樣子。
